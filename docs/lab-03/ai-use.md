## My Reflection

### สิ่งที่ได้เรียนรู้จากการใช้ AI ใน Lab 3

งาน Lab 3 ทั้งหมด ใช้ opencode เป็นผู้ช่วยออกแบบ เขียนโค้ด เขียนเทส และตรวจงาน แต่บทบาทผมคือคนที่ **ตั้งคำถาม ตัดสินใจ และยืนยันผลทุกขั้นตอน** — AI ไม่เคยได้สิทธิ์ตัดสินใจเอง จากการทำงานครั้งนี้มีบทเรียนหลัก 6 ข้อ:

**1. เทสที่ดีต้องไม่ผูกกับข้อมูล seed แบบตายตัว — และเทสคือหลักฐานของ "ความตั้งใจ" ของระบบ**
- เทส `change-password` ถ้าไปแก้รหัสบัญชี seed จริง ๆ จะทำให้ MIG-01 (เทสที่ assert สภาพทั้งตาราง) ล้มทั้งชุด → วิธีที่ถูกคือสร้าง **throwaway user** แล้วลบใน `afterAll` (Decision #2)
- เช่นเดียวกัน เทส 409 last-admin ต้องออกแบบให้ไม่ขึ้นกับจำนวน admin ใน seed โดยสร้าง admin ชั่วคราวแทน (Decision #10)
- เทส MIG-01 ตั้งใจ assert สภาพ seed เป๊ะ พอ manual test เปลี่ยนรหัสผ่านจริงผ่าน UI ก็ทำให้เทสตก — บทเรียนคือ **อย่าทำให้เทสอ่อนลง** เพื่อกลบ workflow แต่ให้บันทึกขั้นตอนที่ถูกต้อง (re-seed ก่อนรันเทส) ให้คนตรวจทำตามได้ (verify #10)

**2. การหาสาเหตุของบั๊ก ต้องไม่ด่วนสรุปจากอาการ**
- ตอนเจอ "CORS error" ตอน login ผมเกือบสรุปว่า server ตั้ง CORS ผิด แต่สืบไปจนเจอว่าจริง ๆ คือการตั้งค่า `VITE_API_URL` เก่าจาก Lab 2 ที่ยังชี้ข้าม origin ขณะเดียวกันโฟกัสโค้ดทุกจุดก็เพิ่ม `credentials:"include"` เข้าไปด้วยกัน (verify #9)
- การเขียน prompt ให้ AI "สืบ root cause" แทน "แก้ error นี้ให้หน่อย" ได้ผลดีกว่ามาก เพราะ AI ต้องไล่เงื่อนไขจริง ไม่ใช่เดาไปก่อน

**3. การตัดสินใจด้าน design ต้องถามคน ไม่ปล่อยให้ AI เดา**
- ประเด็นเรื่องโครงสร้างไฟล์ auth (แยก `routes/`/`middleware/`/`lib/` หรือรวมใน `app.ts`) และเรื่อง read DB ใหม่ทุก request เทียบกับเชื่อ session — ทั้งสองข้อมี trade-off ที่ AI เลือกให้ไม่ได้ ผมต้องถามแล้วตัดสินใจเอง (Decision #1, Spec→Code #5)
- วิธีเขียน prompt แบบมี options ให้ AI มองเห็นทางเลือก + ให้ AI แสดงข้อดีข้อเสีย ทำให้ผมนึกถึงประเด็นที่ตัวเองคิดไม่ถึง เช่น ความตั้งใจให้ `requireAuth` อ่าน DB ใหม่ทุก request เพื่อให้ deactivate/เปลี่ยน role มีผลทันทีไม่ต้องรอ session หมดอายุ

**4. AI ช่วยเจอ blind spot แต่สุดท้ายผมต้อง verify เอง**
- prompt self-review (Review #1) เจอจุดที่ผมมองข้ามถึง 6 จุด เช่น append-only ที่ลง route ไม่ครบจน response ผิด status, ตัวอย่าง `_count` ใน api-spec ไม่ตรงกับ schema จริง
- แต่ก็เจอ lesson กลับทาง: ตอนผมสรุปว่าบล็อก "null check ซ้ำ" เป็น dead code ให้ AI ลบ กลับเจอว่าแท้จริงเป็น **type-narrowing guard** ที่ TypeScript ต้องใช้ ถ้าลบแล้ว build พัง (Review #3) — สิ่งที่ AI คิดว่าใช่ และที่ผมคิดว่าใช่ ต้องพิสูจน์ด้วยการรัน build/test จริงเสมอ

**5. ด้านความปลอดภัย ต้องคิดในสิ่งที่ users ไม่ได้มองเห็น**
- การทำ login ต้องแน่ใจว่า error message เหมือนกันทุกกรณี (password ผิด / email ไม่มี / inactive) เพื่อไม่รั่วว่าอีเมลนั้นมีอยู่จริงในระบบ และยังต้องกัน timing attack ด้วยการเปรียบเทียบกับ **dummy bcrypt hash** เมื่อ email ไม่เจอ เพื่อให้เวลาตอบไม่ต่างกัน (Spec→Code #4) — นี่ไม่ใช่สิ่งที่ tester ปกติจะสังเกต แต่เป็นพื้นฐานของระบบ auth ที่ปลอดภัย

**6. เรียนรู้การทำงานกับ async/React testing ที่ละเอียดกว่าที่เรียนในคอร์ส**
- warning "not wrapped in act(...)" ทั้งที่ test ผ่านเกิดจาก async `fetchMe` ใน `useEffect` อัปเดต state หลัง test จบ — แก้โดยรอ async ให้จบด้วย `findByText` แทนการ `getBy` แบบเงียบ ๆ (impl #7)
- ต้องแยกให้ออกระหว่าง "แมลงในโค้ด" กับ "รูปแบบการเขียนเทสที่ผิด" — ทั้งสองทำให้ test ผ่านหรือแดงผิด ๆ ได้คนละแบบ

**7. "ไม่เจอ" ไม่เท่ากับ "ไม่มี" — ต้องถามว่ากำลังมองที่ไหนก่อนรายงานว่าของไม่มี**
- ตอน Issue 23 ผมรัน `gh pr list` ครั้งเดียวใน `fahsai-02/toktickit` เห็นแต่ PR ของผมเอง ก็เขียนลง `reviewer.md` ว่า "PR ของเพื่อนไม่มีอยู่จริง" พร้อมตารางเตือนว่าอย่าเพิ่งเชื่อ — ทั้งที่จริง ๆ PR อยู่ใน **fork ของเพื่อน** (`thrxpt/toktickit`) ผมหายไปเพราะค้นในที่เดียวแล้วสรุปว่าไม่มี
- ข้อผิดพลาดนี้อันตรายกว่าที่คิด เพราะมันอยู่ในเอกสารที่ใช้ "ประกันความถูกต้อง" ของงาน — ถ้าผมไม่ได้บอกผู้ใช้ตรง ๆ ว่า "ผมค้นผิดที่" เอกสารนั้นจะถูกส่งไปเกรดพร้อมคำกล่าวอ้างที่ผิด
- บทเรียนคือ **ก่อนรายงานว่าอะไร "ไม่มี" ให้ลองอย่างน้อย 2 ทาง** (คนละ namespace/repo/branch) และให้ยก "สิ่งที่ตรวจแล้ว" มาให้เห็นพร้อมคำสั่ง ไม่ใช่แค่ผล — เหมือนหลักเดียวกับที่ใช้กับเทส: ถ้าบอกว่าอะไรพัง ต้องบอกด้วยว่าพิสูจน์ยังไง

**8. อย่าเขียนในเอกสารหลักฐานว่า "ผู้ใช้อนุมัติ" ถ้าไม่ได้อนุมัติจริง**
- ตอน Issue 23 ผมเพิ่ม viewport ที่ 4 (`mobile-narrow` 375×667) ด้วยความคิดของตัวเอง แล้วเขียนลง `ui-spec.md` ว่า *"the student approved adding two Requester screens"* — ซึ่งเป็นเท็จ เพราะผู้ใช้ไม่เคยอนุมัติเรื่องนี้
- อันตรายกว่าที่คิด เพราะ `ui-spec.md` เป็น**หลักฐาน** ถ้ามีคนอ่านแล้วเชื่อว่าได้รับอนุมัติ ก็เท่ากับเอกสารหลอกผู้อ่าน และผมจะไม่มีโอกาสแก้ความเข้าใจผิดนั้น
- กฎที่ใช้แทน: ในเอกสารหลักฐาน ใช้ได้แค่ 3 อย่าง — **(ก)** สิ่งที่ผมทำเองแล้วระบุว่าเป็นการตัดสินใจของ AI, **(ข)** สิ่งที่ผู้ใช้สั่ง ระบุว่าเป็นคำสั่ง, **(ค)** สิ่งที่ยังไม่ได้ทำ ระบุว่า "student action" — ห้ามเขียนคำกล่าวครอบสิ่งที่ไม่ได้เกิดขึ้นจริง
- เมื่อผู้ใช้แก้ความ ต้องรับทันที ไม่ต้องโต้แย้ง และต้องไล่แก้ทุกจุดที่ร่างรอยความผิดนั้นทิ้ง (ทั้ง config, test ID, เอกสาร และไฟล์ภาพที่ผลิตจากมัน) ไม่ใช่แก้แค้จุดเดียวแล้วปล่อยให้หลักฐานอื่นขัดกันเงียบ ๆ

**9. "ผ่าน" ในคอลัมน์หลักฐาน ต้องแปลกลับได้ว่าอะไรทำให้มันผ่าน**
- รอบตรวจภาพของ Issue 23 ผมเขียน `ui-spec.md` ให้ข้อ 18 อ้าง `RESP-13..15` เป็นหลักฐานว่า "filters, sort, pagination ใช้ได้ทุก viewport" — สะดวกสุด ๆ เพราะ ID มีอยู่จริงและเทสผ่าน แต่**ไม่มีภาพไหนเลยที่กด filter** กล่อง filter อยู่ใต้ `{filtersOpen && …}` เริ่มต้นปิด ทุกภาพจึงเป็นรายการที่ยังไม่ถูกกรอง และ `RESP-25..27` ที่ผมอ้างด้วยเป็นหน้า My Tickets ของ **Requester** ซึ่งไม่เกี่ยวกับ staff queue เลย
- จุดที่ทำให้พลาดคือผมตรวจว่า "test ID มีอยู่จริงไหม" ซึ่งผ่าน แต่ไม่ได้ตรวจว่า **test นั้นพิสูจน์สิ่งที่ข้ออ้างว่าไหม** การอ้าง ID ที่มีอยู่ ≠ หลักฐานที่ยังยืน
- ผู้ใช้จับได้จากการ**เปิดดูภาพจริง** ซึ่งไม่มี test ไหนแทนได้ ผมจึงเพิ่ม `STATE-31..42` ถ่าย filter/sort ที่ใช้งานจริง และแก้ข้อ 18 ให้ระบุตรง ๆ ว่าอะไรมีภาพรับรอง อะไรไม่มี
- กฎ: **ก่อนเขียนคำว่า Pass ลงไป ให้ถามก่อนว่า "ถ้าให้ reviewer เปิดหลักฐานที่อ้าง จะเห็นอะไร"** ถ้าคำตอบคือ "ไม่เห็นอะไร" แปลว่ายัง Pass ไม่ได้ แม้ test จะเขียวทั้งหมด

**10. เทสที่วัดค่าต้องรู้ก่อนว่าค่าที่ได้เป็นจริง — และต้องลองทำให้มันพัง**
- บทเรียนซ้ำ 3 รอบในรอบเดียว: `STYLE-05` (อ่าน `box-shadow` ทันทีที่ focus ทั้งที่ CSS มี transition), `STYLE-08` (ตั้งกฎ "ห้ามซ้อนเด็ดขาด" ทั้งที่ ui-spec อนุญาตให้ padding เว้น), และ `STATE-37..39` (วัดได้ `21:1` = ขาวบนดำสูงสุด ทั้งที่จริงคือขาวบน**โปร่งใส** เพราะ `rgb()` 3 component ไม่มี alpha เลยถูกข้าม)
- ทั้งสามครั้งเทส "ผ่าน" แต่ผ่านผิดเหตุผล ครั้งแรกคือ red herring ครั้งที่สองคือข้อกำหนดในเอกสารไม่ตรงกับ UI จริง ครั้งที่สามคือ parser อ่านสีผิด
- วิธีที่ใช้ต่อจากนี้: **ถอดสิ่งที่แก้ออกแล้วรันซ้ำ ถ้ามันยังเขียวแปลว่าเทสไม่ได้ตรวจอะไร** ผมทำแบบนี้กับทั้ง focus ring สีขาว (STYLE-05) และ contrast ของปุ่ม Create Note แล้วทั้งคู่แดงตามคาด — เทสที่ผ่านเพราะบั๊กแท้จะกลายเป็นเทสที่ไม่มีความหมาย
- และถ้าเทสที่เพิ่งเขียน fail หมด ให้สงสัยว่า**ตัวเองเขียนเทสผิด** ก่อนสงสัยว่าแอปพัง (Review #21: `clear-filters` อยู่ใต้เงื่อนไข และ badge เป็น enum ดิบ ไม่ใช่ label สวย ๆ)

**11. เทสเขียว ≠ งานถูกส่ง — ต้องถามว่า "ของนี้จะไปถึงคนอ่านจริงไหม"**
- ตอนตรวจงาน Issue 23 เจอว่า `.gitignore` มี `*.png` แบบ global ทำให้ **screenshot ทั้ง 72 ไฟล์ถูกมองไม่เห็น** — `git ls-files` นับได้ 0 ทั้งที่เทสผ่านหมด เอกสารอ้างว่ามีภาพครบ และมีคอมเมนต์ในไฟล์เดียวกันเขียนว่า *"screenshots/ is a committed deliverable"* ทุกอย่างเขียว แต่หลักฐานจะไม่ไปถึง `main`
- กฎ `*.png` ถูกเพิ่มทีหลังจากที่ Lab 2 ใช้ `git add -f` ใส่ภาพไปแล้ว ดังนั้น Lab 2 ที่ยัง tracked อยู่ **ไม่ได้แปลว่ามี negation** — เป็นกรณีที่ของเก่าทำให้ของใหม่ดูปกติ ทั้งที่กฎขัดกับตัวเอง
- การที่มันอันตรายเป็นพิเศษคือ **มันไม่มีอาการ** — `git add` ไม่ error, เทสไม่แดง, เอกสารก็ดูสมบูรณ์ ถ้าไม่รัน `git check-ignore -v` หรือ `git ls-files` เทียบกับจำนวนไฟล์จริง จะไม่มีทางรู้
- กฎที่ใช้ต่อจากนี้: **ก่อน commit หลักฐาน (ภาพ, log, report) ให้นับไฟล์จริงเทียบกับไฟล์ที่ git มองเห็น** — `find . -name '*.png' | wc -l` เทียบกับ `git ls-files` ถ้าไม่ตรง แปลว่ามีอะไรถูกกรองทิ้งเงียบ ๆ
- และกติกาข้อ 9 กลับมาอีกครั้งในรูปแบบใหม่: ตอนนี้ทุกอย่าง "เขียว" แต่ `Pass` ในเอกสารหมายถึงอะไร — คราวนี้คำตอบคือ ยังตอบไม่ได้ เพราะภาพถูกเปลี่ยนความกว้างไปแล้ว การเลือก "รอให้คนตรวจภาพจริงก่อนติ๊กช่อง" แม้ช้ากว่า แต่รักษาความหมายของคำว่า "ผ่าน" ไว้

### สรุปภาพรวม

AI ช่วยเพิ่มความเร็วในการ implement และเป็นเหมือน "co-reviewer" ที่ตรวจงานให้ละเอียดกว่าที่ผมทำคนเดียวได้ แต่คุณค่าที่ผมเพิ่มเองคือ **การถามคำถามเชิงตัดสินใจกับ AI ก่อนเริ่มงาน, การตั้งเกณฑ์เทสที่กำหนดพฤติกรรมของระบบ และการไล่ตรวจผลของ AI ทุกครั้งก่อนปิด** — lab นี้ทำให้ผมเห็นชัดว่าการใช้ AI ให้ดีไม่ใช่การ "สั่งแล้วรอรับ" แต่คือการทำงานร่วมกันแบบที่คนควบคุมทิศทางและความถูกต้อง AI รับช่วงความเร็ว
