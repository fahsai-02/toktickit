## My Reflection

Lab 4 ใช้ AI ช่วยวางแผน เขียนโค้ด เขียนเทส และรีวิว แต่ทุก decision ที่เปลี่ยนสัญญา (สเปก, ขนาดปุ่ม, รูปแบบกล่อง Urgent, ข้อยกเว้นของ Lab 2) เราเป็นคนอนุมัติเอง และเอกสารที่แก้ต้องผ่านการอนุมัติก่อนทุกครั้ง

**1. "ตรวจแล้ว" ต้องครอบคลุมทั้งช่วงที่เอกสารกำหนด ไม่ใช่ตัวอย่างเดียว**
- เรื่อง layout shift ถูกแก้ถึง 4 รอบ เพราะรอบแรกวัดแค่ลิสต์ 3 แถว ทั้งที่ API คืนได้ถึง 5 และ 10 แถว (prompt 5)
- กฎที่ได้: ก่อนบอกว่าเสร็จ ให้ไล่ทุกขอบเขตที่เอกสารระบุ (ว่าง / กลาง / สูงสุด, ทุก role, ทุก viewport) และบอกด้วยว่าอะไรยังไม่ได้ตรวจ

**2. เอกสารที่เขียนว่า Pass ต้องมีการรันจริงรองรับ**
- การรีวิว Issue 27 เจอว่าโค้ดและเทสถูกต้องทั้งหมด แต่ `tests.md` ตั้ง `Pass` ไว้ก่อนมีบันทึกการรัน ซึ่งขัดกับประโยคที่เอกสารเขียนเอง (prompt 3)
- ใน Issue 29 จึงพลิก `Planned` → `Pass` หลังรันจริงเท่านั้น (209 passed / 0 failed / 73 skipped) และเขียนรายการข้อยกเว้นไว้ตรง ๆ แทนการซ่อน (prompt 7)

**3. ข้อกำหนดที่ไม่มี test รองรับ จะถอยหลังได้ทุกเมื่อ**
- กฎ tap target ใน ui-spec section 6 ไม่มีแถวทดสอบใดวัดเลย จึงเพิ่ม `STYLE-11` ที่วัดความสูงจริงที่ 375px (prompt 7, 9)
- ตอนจะบังคับ 44px ก็เจอผลข้างเคียงจริง (pagination ตกบรรทัด) ซึ่งอ่านสเปกอย่างเดียวไม่เห็น ผมจึงเลือก 36px แล้วแก้สเปกให้ตรงกับของที่ส่งจริง

**4. ไม่เชื่อคำกล่าวอ้างจนกว่าจะตรวจกับหลักฐานจริง ทั้งของเพื่อนและของ AI**
- ข้อที่เพื่อนว่า CSS อยู่นอก `@layer layout` ไม่จริง ตรวจจาก bundle ที่ build แล้วจึงไม่แก้ (prompt 4)
- ในทางกลับกัน เทสที่เขียวอาจเขียวเพราะวัดไม่เป็น จึงต้องถอด fix ออกชั่วคราวให้เห็นว่ามัน fail จริงก่อนเชื่อ (prompt 6, 10)

### สรุปภาพรวม

AI ทำให้ไล่เทียบสเปกหลายไฟล์และรันทดสอบจำนวนมากได้เร็วกว่าทำคนเดียว แต่ส่วนที่ผมต้องรับผิดชอบเองคือ การตัดสินใจเมื่อสเปกกับของจริงขัดกัน, การกำหนดว่าอะไรนับเป็นหลักฐาน, และการไม่ปิดงานก่อนตรวจครบทั้งช่วงที่กำหนด
